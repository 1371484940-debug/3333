# 中文需求文档撰写

交付目标：读者能直接确定本次新增什么、改变什么、影响哪里，并根据规则实现和验收。使用用户的模板与项目术语；完整程度以本次范围内的行为能否确定为准。

## 1. 判断当前任务

| 任务 | 输出范围 |
|---|---|
| 新增完整功能，或明确要求全量说明 | 展开所要求功能的完整流程、页面及必要关联规则 |
| 现有功能增量改造 | 展开新增、变化和由此造成的直接影响 |
| 局部修订 | 修改指定内容，同步受影响的引用、表格、示例和验收；保留其他原文 |
| 解释现有逻辑 | 回答问题；若需纠正文档，只修正相关表述，不将调查结果自动变成新需求 |

撰写包含交付自查。用户仅要求审查时，先交付问题及依据；完整审查可使用可用的专用审查技能，不因审查请求自动改写正文。

## 2. 先决定哪些内容写入正文

完整功能按用户指定的范围展开。以下纳入条件用于增量文档及局部修订中新写入的内容，不用于删减用户要求的全量说明。

写作前从用户已明确的要求、修正和批准中识别变更。每个拟写入的功能点须属于以下之一：

1. 本次要求新增的功能。
2. 本次要求改变的原有行为。
3. 为使上述功能成立，必须同步改变的关联行为；能够说明“不调整这里，会使哪条本次规则失效”。
4. 理解上述变化不可缺少的原有前提；只简短说明或引用必要部分。

前三类详细写。其余调查结果不进入本次需求正文；调查范围可以大于文档范围。发现独立的既有缺陷或改进机会，不自动列入改造和验收。判断不清时先核实其与本次需求的关系，不继续补全额外功能的权限、异常和提示。

复杂任务用内部清单记录 `功能点｜依据｜新增/调整/直接影响｜页面或入口｜调整后行为`，小改动直接确定即可。不要求额外输出范围报告或等待阶段审批。

**仅增加前置限制时：** 写清新增限制、检查时机、拒绝反馈和解除后的行为；原有业务判断未改变时，可写“其余沿用原有规则”，不重抄全部判断。若新行为取决于某项旧条件，核实并说明该必要条件。不得用“沿用原规则”省略本次新规则。

## 3. 核实依据，再组织页面

- 复用用户的最新明确决定。原型说明可观察的页面行为，代码补充当前实现与关联关系；二者都不能把未授权的功能变为需求。自己新做的演示也不能证明某项设计属于原有业务。
- 对本次涉及的原型实际查看页面、状态、入口和弹窗；静态截图只证明可见部分。记录可定位的来源或版本，不将旧图、新代码和运行中的旧页面混作同一现状。访问受限时写明未核对范围，继续完成有依据的规则。
- 描述现状时只采用项目真实存在的业务对象和状态；新增对象、状态和操作须来自本次要求或完成该要求所必需的设计。模板例子、历史字段、演示数据不构成扩展业务范围的依据。
- 同一资料有冲突时先查已确认记录。普通布局和提示优先沿用项目约定，自主补齐低影响细节；不能确定且会改变权限、业务结果或数据处理的决定，就地标明待确认及影响，不编造答案，也不阻塞无关部分。

功能点按业务先后排列，无先后关系时按重要程度组织。页面内按实际布局和操作顺序说明，通常从上到下、从左到右，先展示及输入，再操作和校验。关联影响放在受影响页面；确需单独章节时精确引用，避免同一规则多处维护。

## 4. 按需选用模板与写法

- 新建文档或调整目录时，读取 [模板标准](references/template-standard.md)；用户已有结构优先，局部修订不重新套整份模板。
- 详细写功能时，按改动类型选读 [功能写法](references/writing-patterns.md) 的对应章节：字段调整、流程、多状态、列表管理、统计或页面展示。一个需求可以组合多种写法，无需逐类展开。
- 本次改变 AI 生成、分析或摘要行为时，再读 [AI 功能规范](references/ai-feature-specification.md)。仅调整既有 AI 入口的可见性，无需展开生成流程。
- 写完按 [交付检查](references/quality-gate.md) 依次核对范围、事实、具体行为、一致性和冗余，修复可确定的问题后交付。

## 5. 修订与正文表达

- 标题直接指出页面及变化，例如“详情页：已归档时隐藏维护操作”。未改变原有判断时，不命名为整套业务规则改造。
- 用业务名称说明具体条件和结果；“符合条件”“相关提示”“按权限”等需要明确依据。“隐藏”“置灰”“可点击”“允许执行”分别描述。提示语有必要时给出准确文案，不把每段业务解释变成页面提示。
- 正文写产品行为和可观察结果。接口、数据库、技术状态码、锁、队列、部署命令及模型参数不进入默认 PRD；用户另有要求时单独交付。失败后数据如何处理属于产品规则，采用什么机制实现属于技术方案。
- 用户修改范围或规则后，同步清理正文、表格、示例、验收和授权范围内的关联文档。删去被放弃方案的残留，不通过逐项声明“不支持”再次介绍；业务本身的禁止条件仍须写清。
- 关键规则用稳定章节条款号或规则 ID，引用指向具体定义。局部修订尽量保留编号。正文保留最终规则，不放调查流水、写作自评、空模板及不必要的旧功能说明。
- 最终交付简述改动和实际缺口。文档自查、原型核对与产品实现分别据实说明，不用文档完成代表功能已实现或测试通过。
