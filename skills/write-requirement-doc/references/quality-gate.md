# 交付检查与验收

完整需求、详细功能说明及需求审查使用本检查；默认只检查本次新增、调整和实际关联影响的交付范围，全量说明以用户明确要求为准。内部可以核实旧规则，但不将未变化旧功能重复写入正文，不逐项播报检查过程。

## 1. 覆盖检查：每个功能是否真正展开

对照工作清单，为每个页面/区块/动作找到规则位置或明确缺口：

- 原型/需求中属于本次新增、调整或实际受影响的页面、区块及子界面是否都有对应说明？是否仅写了名称？
- 本次涉及的字段和枚举能否找到定义或必要引用？动态选项的来源和范围是否明确？
- 本次涉及的操作是否有触发、条件、处理、结果及适用失败行为？受影响的流程衔接是否遗漏？
- 关联模块的变化是否有落点，引用是否真的指向对应规则？
- 区块的辅助文案、字段提示、状态配套说明和操作反馈是否有落点？是否只写业务字段，漏掉条件变化后出现的文字？
- 正文是否按本次改动页面组织？阅读单页章节能否确定其受影响元素的具体行为，而不需要开发自行补规则或跨主题拼接页面表现？
- 有原型时，是否核对了本次涉及的实际页面、状态与入口，而不只是读了代码或默认首屏？字段、文案、弹窗及交互是否都有相应证据位置？未能核对的部分是否如实标明？

不得通过自行删除难写区块、编造默认值或把所有缺口都塞进文末使覆盖表看似完成。

## 2. 可执行检查：同样输入能否得出确定结果

从开发和测试视角核对，而不是检查是否出现了“权限”“异常”等词：

| 检查对象 | 判定问题 |
|---|---|
| 条件 | 哪些条件同时满足或任选其一？临界值是否包含？数据变化后用哪个时点判断？ |
| 展示 | 能否确定各区块、字段、文案、顺序、格式、点击行为及适用页面状态？ |
| 文案与提示 | 固定文字、动态变量、触发方式、呈现与关闭行为是否明确？“如有”“相应提示”是否有可追溯条件？ |
| 状态展示 | 状态属于哪个对象，各值的标签、配套说明及相关元素变化能否逐一确定？ |
| 输入 | 能否确定完整选项、范围、必填、联动、校验及错误处理？ |
| 状态 | 给定当前状态和事件，能否确定成功流转或拒绝及其结果？ |
| 权限 | 能否分别判断可见、可操作、数据范围和执行时的拒绝结果？ |
| 数据 | 成功改变什么、保留什么，失败是否留下部分结果，关联数据是否变化？ |
| 统计 | 用同一小样本是否能算出唯一结果，并解释零分母和时间边界？ |
| 恢复 | 失败后界面与输入处于什么状态，用户如何重试或确认结果？ |

将“支持筛选”“校验通过后保存”“按权限展示”“记录变更动态”“异常时提示”等句子作为定位线索；只有其缺少具体定义或精确引用时才判为缺口，不靠关键词命中自动判错。

## 3. 一致性与范围检查

- 术语、必填字段、枚举、状态、按钮条件、权限范围在正文、表格、示例和验收中是否一致？
- 当前值与历史事实、业务状态与展示标签、计划金额与实际金额是否被混用？
- 流程图中的转换、正文中的校验、状态表中的结果能否互相对应？
- 正常空值与违反业务约束的数据异常是否区分？没有数据与读取失败是否被混写？
- 用户最后一次修正是否同步到相关章节、文案、验收和关联文档？用户已明确排除的概念是否仍残留于业务规则或示例？
- 原型未体现的业务规则是否有依据或标明待确认？是否仅凭演示数据、模板例子或历史项目设定扩大范围？
- 文档描述的是产品结果，还是未经要求指定了代码、接口、数据库和框架？
- 正文是否清楚描述最终产品？已放弃方案是否通过“不展示/不支持”反复出现？必要权限和状态限制是否仍保留？
- 兼容场景和额外字段是否有业务依据，还是把历史可能性或演示分支写成了必做能力？
- 页面辅助文字是否参考现有同类页面，是否把仅供研发理解的业务解释塞进了页面，或重复已经展示的信息？
- 涉及 AI 能力时，分析范围、结果内容与页面展示是否一致，事实准确性和内容质量是否有验收依据？仅在用户明确要求另行交付提示词时核对其与产品规则的一致性。按 [AI 功能规范](ai-feature-specification.md) 检查适用部分。
- 是否为了显得完整，加入原型和明确需求都没有的功能、字段、提示或假想异常？补充原型外内容是否能指明具体原型问题、必要缺口或已确认依据？
- 是否有无关背景、过程叙述、自评、重复解释或不适用的模板段落可以删除？精简后必要的逐元素条件、交互和结果是否仍完整？
- 每段内容能否对应本次新增、调整、实际影响或不可缺少的前提？是否因为原型展示了完整旧页面，就重复写入旧字段、按钮、分页和权限，或逐项声明“不变”？这些内容没有必要关联时应删除。
- 对现有功能的真实影响是否具体写清受影响位置、调整后结果及生效范围？是否仅写“兼容原功能”而漏掉历史记录、筛选、导出或统计中实际变化的规则？
- 是否混入接口、请求结构、数据库表列、代码、技术状态码、缓存、队列、部署或测试命令？应转写为必要产品结果或移出正文；“实现时用得上”不等于产品需求必须写。
- 是否基于同一确认版本对照原型与文档？页面字段、名称、顺序、选项、默认值、提示形式、交互和状态显示是否逐项一致，且正文、表格、示例、验收没有各写一套？
- 双向检查是否完成：原型内的本次内容没有漏写，文档中的页面描述没有无依据增加或改变？必要原型修正是否简明标出了具体问题和依据，未冒称当前原型已实现？
- 如果原型在写作期间更新，受影响条款是否重新核对？是否把旧截图、源码新版本和运行中的旧页面混成了一份现状说明？

## 4. 规则与验收对应

关键规则使用稳定章节＋条款号或规则 ID。场景不必与段落一一对应，但应能追踪回规则；同一场景可以验证多个相关规则。无需为每句文案生成测试用例。

| 场景编号 | 对应规则 | 前置条件与输入 | 操作/事件 | 预期页面结果 | 预期数据及关联结果 |
|---|---|---|---|---|---|
| AC-01 | 具体规则位置 | 角色、状态和必要边界值 | 明确动作 | 可观察的展示、反馈、刷新 | 新增/变更/不变或不适用 |

验收围绕本次新增、调整及实际影响，按适用性覆盖正常完成、拒绝、临界值、状态变化及必要组合；不将原页面完整旧用例库重抄进本次需求。必要时验证与旧功能的实际衔接，避免对所有角色×状态×字段做无意义全排列。

复杂正文需要展示样例；计算需要具体输入和验算结果；状态操作需要成功与拒绝结果。验收不能只写“符合规则”“保存成功”或只检查提示而忽略数据。

对于有状态说明或交互提示的页面，选择实际存在的状态、入口和触发动作核对：标签与配套文字一致出现，变量替换正确，提示后停留/关闭/跳转符合规则。不要只验收状态名而漏掉说明文字，也无需给每个普通固定字串单独建立用例。

## 5. 待确认事项与完成判断

| 编号 | 缺失决定或冲突 | 已知依据/建议（明确区分） | 影响规则 | 阻塞的开发或验收范围 | 可独立推进部分 |
|---|---|---|---|---|---|
| Q-01 | 写成可回答的问题 | 不把建议当确认 | 指向具体条款 | 说明实际影响 | 列出不依赖此决定的部分 |

待确认表只收录实际需要决定或存在关键依据缺口的事项。普通展示优先复用已有约定，不为每个未指定的样式另列建议或问题。为修正原型问题或完成已有功能而必要补充的低影响规则，可注明依据后继续推进，不单独造成“不可开发”结论；不得借此引入非必要内容。用户明确要求先确认该项时仍保留确认边界。

根据事实区分交付状态：

- **可开发验收**：当前范围关键行为有明确依据和规则，适用检查通过，无影响该范围实施的关键待定项。
- **部分可开发验收**：有具体待定项，明确哪些部分可推进、哪些需等决定；不把待定部分写成唯一行为。
- **待确认草稿**：核心流程、权限或计算口径仍未确定；交付已完成内容和聚焦问题，不宣称完整。

这些状态用于诚实表达交付成熟度，不要求每篇文档增加固定状态页或等待用户批准。

“规则可开发验收”与“已核对原型”分别判断。原型访问受限不自动否定已有明确规则，但应限制关于原型一致性的结论；未经实际对照不得写“已完全按原型核对”。

修复自己能够依据现有资料解决的缺口后再交付。自查不等于已经由研发、测试或业务实际评审，未做的验证不得宣称完成。
