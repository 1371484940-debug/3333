# 交付检查

按下列顺序自查本次交付。不要求生成检查报告或固定数量的验收用例；完整审查另按用户任务处理。前一步发现范围不成立时，先移除或澄清该内容，再检查其余部分的细节。

## 1. 范围：有没有多写或漏写

- 正文中的每个功能，能否对应本次新增、调整、必要关联影响或不可缺少的前提？原有完整文档中保留的未改原文不算新增范围。
- 是否把解释旧逻辑、代码调查、独立缺陷或模板范例转成了新增需求？若移除该额外改造，本次功能仍可按要求成立，就重新检查其依据。
- 是否漏掉某项真实影响，导致本次规则不能成立？例如只隐藏入口，却没有定义旧页面继续提交时如何执行本次状态限制。
- 标题和范围表是否准确表达变化？仅增加前置限制时，是否被写成重做原有删除、导入或权限机制？

范围过大时删除多余要求及其验收，不继续完善多余功能。范围遗漏时补足有因果关系的变化，不扩展成整个关联模块的重写。

## 2. 事实：有没有把推测写成已知

- 功能名称、业务对象、状态及已有操作是否有项目依据？自己制作的演示和旧字段是否被当作既有业务事实？
- 用户最新决定是否已落实？冲突及关键未知事项有没有就地标出，正文是否又把它写成确定结论？
- 原型是否实际核对了本次涉及的页面、入口、弹窗和状态？截图是否展示正确场景，是否有遮挡、旧文案或无关浮层？不能仅凭文件存在就宣称截图正确。
- 所依据的页面与资料是否为同一确认版本？原型变化后只复核受影响内容；无法访问的部分据实说明。

## 3. 行为：开发和测试能否得出同一个结果

仅检查本次涉及的类型，按 [功能写法](writing-patterns.md) 的相应章节补缺口：

| 对象 | 判定问题 |
|---|---|
| 筛选、字段、展示 | 位置、选项/来源、默认值、条件及格式是否足以确定结果？ |
| 入口与弹窗 | 是否区分显示、可点和允许执行？点击后内容、按钮及关闭/停留/刷新能否确定？ |
| 操作与状态 | 条件之间的且/或关系、检查时点、成功和拒绝后的数据及页面结果是否明确？ |
| 权限与配置 | 本次新增配置控制哪些动作，如何生效，既有角色如何处理？普通旧权限是否只作必要引用？ |
| 统计 | 同一输入能否算出唯一结果，适用的时间、去重和零分母口径是否明确？ |
| 关联影响 | 哪个页面/对象因此改变什么，哪些已有数据受影响，能否确定最终行为？ |

“按原规则”“同新增”等有明确适用范围且确实未变时可以保留；本次变化尚无定义时不能用这些表述替代。判断内容是否缺失，不用关键词命中或表格数量判断质量。

## 4. 一致性与修订清理

- 正文、表格、流程图、文案示例和验收使用同一套条件和结果；精确引用能找到定义，编号调整后同步更新。
- 从页面检查本次元素是否漏写，再从文档检查是否凭空增加元素或操作；有依据的原型修正标明差异。
- 用户收窄范围或删除方案后，关联正文、示例、验收和授权范围内的配套文档是否一起清理？不要把已经取消的方案以“暂不支持”继续写入正文。
- 默认正文中是否混入调查过程、接口、数据库、部署及技术方案？移出不属于产品规则的内容。
- 删除重复旧规则、无关背景、空表和自评后，当前页面的必要条件与结果是否仍完整？

## 5. 验收与完成判断

关键改动应能对应具体的前置条件、操作和预期结果。简单功能可直接使用规则条款作为验收依据；复杂状态或关联变化再列场景。验收仅覆盖本次改动及必要衔接，不重抄旧功能用例库，不为每个字串另建用例。

可采用：`对应条款｜前置条件/输入｜操作｜预期页面及数据结果`。根据实际风险覆盖正常、拒绝、边界和状态变化；无需做所有角色、状态、字段的全排列。计算给可验算的小样本，失败场景同时核对提示与数据结果。

能依据已有资料解决的缺口直接修正；实质影响结果且无法确定的决定就地说明已知依据、缺失决定及影响范围。多个待确认事项可集中汇总；普通布局和沿用项目规范的细节不逐项升级为待确认。

交付说明区分：规则已经明确、哪些部分仍待决定、哪些原型尚未核对。文档自查不代表研发测试已评审，也不代表产品已实现。没有剩余缺口时简要交付文件即可。
