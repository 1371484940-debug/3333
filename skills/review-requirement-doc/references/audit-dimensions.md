# 审查维度与判定方法

以下十个维度按本次新增、调整及实际关联影响选择；全量审查以用户明确范围为准。维度用于检查规则，不是强制文档目录。适用部分区分“充分、部分缺失、缺失、无法验证”，无关部分标为“不适用”或省略；有缺口时关联具体问题，不用章节有无或关键词命中代替判断。同一根因涉及多个维度只记录一次。

## 1. 范围与功能覆盖

将已确认功能/原型区块与文档章节映射，检查：遗漏整个页面、仅列区块名未展开、操作承诺没有后续处理、流程分支没有终点、引用位置不存在。区分本次范围与未来设想。

背景和目标用于理解范围，不因缺少漂亮的背景描述就阻塞局部字段需求。没有外部基准时，只能判断文档内部承诺是否闭合，不能宣称覆盖了用户未提供的全部业务。

增量需求只核对新增、调整与实际受影响部分。既有页面其他区块的完整说明不属于本次默认交付；补写建议必须指出范围依据或操作无法闭合的具体环节。已承诺能力整体未提及属于功能遗漏；能力已写但取值、条件或结果不足属于规则遗漏或歧义，不能一概建议“新增功能”。

## 2. 页面展示与文案

在本次新增、调整及受影响的区块内核对以下内容；新页面或明确要求整页审查时再检查完整页面结构：

| 检查对象 | 缺口判定关注点 |
|---|---|
| 展示条件 | 何时出现、隐藏、只读或置灰，是否混淆无数据与不适用 |
| 数据范围与来源 | 显示哪些记录、来自什么对象，当前值/历史值/计算值能否区分 |
| 内容与结构 | 列表列、卡片字段、标签、顺序、单位和格式能否确定 |
| 数据组织 | 默认排序及同值处理，数量上限、分页或加载方式是否明确 |
| 页面状态 | 正常无数据、读取失败、无权限和加载中是否混为一种空态 |

动态、时间线、通知等结构化内容，区分“记录什么业务事实”与“页面具体显示什么”。检查类型完整枚举、触发条件、标题、正文数据及顺序、操作人与时间、长内容、链接行为；需要可比对的正文模板或例子时指出具体缺失。不是所有文案都要求固定逐字模板。

未规定图标颜色、像素间距或普通提示措辞，若已有设计系统或不影响规则判定，通常属于可选改善；缺少整个区块内容、点击结果或必要失败处理则可能影响实现。不要把所有细节一律降为样式，也不要把所有样式缺失升级为阻塞。

辅助说明、字段提示、状态配套文字和操作反馈属于可见内容，不只盘点业务字段。检查实际需要的固定文字、动态变量、出现条件、呈现方式及关闭/消失行为；提示随状态变化时核对标签和配套说明是否一致。“如有则提示”“显示相应原因”若无法确定触发条件或内容，定位具体缺口。文档中的业务解释不自动成为页面必须显示的文案。

## 3. 交互与操作流程

围绕本次涉及的入口、操作和子界面，检查“谁在什么条件下 → 如何触发 → 输入或选择 → 判断 → 页面及业务结果”的相关步骤。

- 区分整行、名称和按钮的点击行为；打开页面、弹窗或抽屉后，当前操作所需内容和动作是否明确，不能以“打开编辑”替代定义。
- 页签切换、返回、取消、关闭是否影响当前输入、选择或已有结果；只核对实际存在的动作和影响。
- 提交成功后关闭、停留、跳转或刷新什么，失败后保留哪些输入、如何再次操作，是否可从原文或公共约定确定。
- 显示条件、可操作条件与执行结果是否一致；某状态下没有入口，不等于已经定义了所有入口的业务限制。

这些维度用于定位具体行为，不要求为一次字段改动重复整页旧流程；与展示、异常维度发现同一缺口时只报一条。

## 4. 字段与数据规则

- 字段是否区分必填、条件必填、默认值、编辑回填、可编辑条件及联动清理；不同表格是否相互矛盾。
- 固定枚举是否完整，动态选项是否有明确来源、范围及停用值处理；没有依据时不自造选项。
- 数值、长度、日期是否明确范围端点、精度、单位和适用时区；输入合法性是否与展示格式混淆。
- “不可重复”是否说明比较对象、唯一性作用域及相关规则；公共定义已解决的不要重复报缺失。
- 查询字段与匹配方式、多个条件组合、触发、重置、日期归属能否确定。页容量可调整却没有选项且无公共规则时才报告缺口。
- 校验在何时发生、错误如何反馈、提交失败是否保存或丢弃输入；前端输入限制是否被误当作业务允许范围。

边界例子使用原文允许的输入，不随意增加项目不支持的日期类型或异常字符策略。

涉及计算或统计时，再检查以下口径：

确定统计对象、最小计数单位、纳入与排除条件、去重、时间字段、时间边界、公式、单位、舍入、更新和历史更正。

构造能暴露歧义的小样本，实际验算：分子分母是否同一集合、重复记录是否重复计数、零分母与真实零值是否区分、跨月或归属变化是否改变历史值。选择需求实际涉及的情形，不强制添加所有统计边界。

展示标签可能简化状态；检查完整状态到标签的映射是否完整，排序和统计是否误用展示标签。示例数值、公式文字、表格和验收预期应能互相验证。

## 5. 业务逻辑与状态

识别对象、状态、事件和判断条件。以转换表或工作笔记核对当前状态＋事件＋前提是否有唯一结果；对比流程图、正文、按钮表和状态表。

检查不可达状态、没有处理的分支、互相冲突的前置条件、目标状态不一致、取消/撤回后数据处置不明，以及适用的驳回重提、超时等规则。仅在已有范围包含对应动作时要求这些分支。

用具体场景验证先后关系，例如“待审批仅可查看”与同状态“允许审批通过”在同一用户条件下是否冲突；角色条件不同且定义清楚则不能误报。

条件表达检查“同时满足/任一满足”、比较端点、处理优先级和无匹配分支。已有统一拒绝规则可覆盖禁止转换，不要求逐格重复写禁止。

术语、引用及跨文档关系也按同一适用条件核对：

检查同名不同义、异名同义、版本混用、正文与表格冲突、修正后的旧例子残留、历史字段和当前字段混用。不同状态或入口下的明确差异不是冲突。

引用公共规则时先读实际内容；引用可复用校验和口径，但不能使当前页面的内容、结构和交互消失。引用损坏或取不到资料时，说明何处无法验证，不编造被引用规则。

## 6. 权限与适用约束

分别检查能否进入、能否看到数据、能否执行动作和数据范围。角色名称本身不能替代配置式权限的定义；用户已确认固定角色方案时也不能强行改成动态配置。

核对实际涉及的列表、详情、搜索、统计、导出、候选选项和直接访问是否执行一致或明确有差异的口径。按钮不可见不能单独证明操作被拒绝；能查看非本人记录不自动意味着可编辑。

归属变更后，当前责任、历史经办人、记录可见性是否混淆。配置需求检查作用域、默认来源、生效时机、优先级与历史业务影响。不要为了审查而发明业绩归属、多身份或新权限体系。

性能、安全、兼容性只检查本次明确要求或实现该业务结果必需的产品约束，例如适用终端、允许的可见范围、已承诺的用户等待时间；不因缺少独立章节而报错。不默认要求接口、数据库、加密算法、缓存、技术框架或部署方案，也不自行设定性能指标。

## 7. 异常与边界

围绕本次操作检查实际适用的输入端点、空条件、正常无数据、读取失败、重复触发、保存失败、输入保留、操作时业务状态已变化、批量部分不符合条件等情形。每个问题须说明在什么条件下哪个产品结果无法确定，不无边界罗列假想故障。

批量操作关注全部失败或允许部分成功、已成功项是否保留、失败项如何展示、重试目标是否重复处理。跨对象操作关注必须共同生效的结果、失败时是否残留成功状态或记录。实现采用什么技术机制不属于默认 PRD 缺陷。

字段允许范围、日期端点及校验见字段维度；同一处缺失不再次登记为“边界缺失”。失败、重复操作和同时操作检查业务结果，不要求“幂等、事务、锁、队列设计”等实现机制。

## 8. 现有功能与关联影响

将本次改动与实际依赖它的现有页面和业务规则对应，检查“受影响位置 → 本次变化 → 调整后结果及适用范围”是否明确。按事实核对历史记录、筛选结果、导出、统计、状态、权限或配置生效范围；它们是可能的影响位置，不是每份需求都必须写一遍的清单。

删除、停用、交接、配置调整等已存在操作，应明确必要的引用限制、关联对象处理、历史事实及可见性变化。不要默认级联删除或自动新增补偿系统。

例如新增字段确实进入已有导出时，应核对导出列与取值；不能因为新增字段，就自行要求增加导出能力。历史记录如何展示或参与计算属于产品规则，通过什么表结构或迁移脚本实现不属于默认 PRD 审查。只写“兼容原功能”而未说明已确认的实际变化，仍是不完整。

## 9. 原型与文档一致性

存在原型时，先确认对应版本、本次变更范围及用户已明确覆盖原型的修正，再对照相关页面、入口和可取得状态。双向核对：本次原型内容是否有文档落点，文档中的界面规则是否有原型或已确认需求依据。

核对字段及区块名称、顺序、选项、默认值、展示格式、提示文字与呈现形式、入口动作、弹窗内容、状态变化等；必要时同步核对正文、表格、示例和验收，避免不同位置各写一套。

差异应列出文档位置和原型证据，说明同一场景下的不同表现。用户已确认修改，或有依据的必要原型修正，应检查是否明确说明，不机械要求回退到旧原型。演示数据不自动成为枚举、上限或固定业务规则。

无原型且任务未要求提供时，该维度不适用；原型已被指定但无法访问、状态未能打开或版本不明时，记录相应部分无法验证。截图只能证明可见表现，源码不等于已验证实际交互。受限部分不判“与原型一致”，也不判原型或需求漏写。

## 10. 可验收性

尝试为关键规则写出“前提＋输入＋动作＋页面预期＋数据预期”。如果无法得到唯一预期，定位是哪项规则缺失或矛盾，而不是只建议“增加测试用例”。

验收场景检查与正文是否一致，是否只写“处理正确”，是否忽略必要的数据及关联结果。没有独立验收章节不必然是缺陷：正文足够可判定时可直接推导测试；用户要求独立验收章节而缺失时按明确交付要求报告。

检查待确认问题是否就地关联受影响规则，建议是否被写成已确定政策，核心待定项是否被掩盖在“已完整可开发”的结论中。已明确标注的业务决定不当作作者逻辑错误，但应说明它仍会阻塞哪些实施或验收。

普通、可逆展示建议可直接给出且注明；关键业务决定需指出要决定什么。缺少数据库表结构、接口名称、技术框架等通常不是产品需求文档缺陷，除非用户明确要求相应技术规格交付。

缺少独立性能、安全或异常章节同样不自动构成缺陷，应检查实际业务约束是否已有可定位定义。修复验收须能在具体场景中判定问题消除，不要求为每句固定文案新增测试用例。
