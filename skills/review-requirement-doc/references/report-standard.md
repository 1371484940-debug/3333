# 问题报告标准

输出供产品修订、开发澄清和测试验收使用的具体报告，避免通用检查清单式结论。用户有报告模板则优先适配，但保留定位、证据、影响与修复条件。

## 1. 先分类，再按影响定级

| 分类 | 判定依据 | 报告方式 |
|---|---|---|
| 确定缺陷 | 可读资料证明遗漏、矛盾或多义，且影响本次范围 | 纳入问题清单并定级 |
| 待确认业务决定 | 文档已明确未定，或某个已定位缺陷的修复依赖实际业务选择 | 单列决定及影响，关联缺陷编号；若正文同时断言相反口径，再报真正矛盾 |
| 验证受限 | 相关附件/原型/引用未取得、无法读取或未审到 | 列清范围和原因，不当成已证实漏写 |
| 可选改进 | 规则已可判定，只改进表达、阅读或普通视觉一致性 | 简短单列，不计入阻塞缺陷 |

未说明且未标注的必要业务规则，属于可证实的遗漏或歧义；即使修复需要业务决定，也应在缺陷清单说明严重程度，并关联需要确认的问题，不将遗漏悄悄移出缺陷清单。已明确待定且交付边界清楚的事项则不重复计作作者缺陷；同一个根因不因同时出现于问题和决定表而重复计数。

确定缺陷使用以下严重程度；按具体后果判断，不按主题机械定级：

- **S1 阻塞**：核心操作/状态/权限/数据结果互相冲突，无法确定应实现哪一种行为，或可导致明显错误的数据或权限结果。指出具体被阻塞的功能，不因此宣称其他独立模块不能开发。
- **S2 重要**：功能主线明确，但局部行为、页面区块、边界或异常不完整，容易产生不同实现或漏测，交付该部分前需补齐。
- **S3 一般**：存在有证据的局部表达或定位问题，影响理解或维护，但不改变主要业务结果；说明具体影响，不收集无关排版偏好。

用户另有级别体系时映射说明。不要默认为所有问题打分或生成百分制“完整度”；问题数量不能直接证明文档质量。用户确实需要评分时，先说明维度、权重、可审范围和受限项，评分不能替代明细。

## 2. 报告结构

### 审查结论与范围

简述已审文件/章节/版本、依据和实际结论，指出优先解决的问题及涉及范围。结论与问题清单一致，不一边存在 S1 一边说可以直接完整交付。

完整审查附简短覆盖表：`页面/流程｜已审区块或步骤｜覆盖状态｜问题编号`。较小片段可以用一句范围说明代替。尚未读取部分单独列明。

### 具体问题

问题少时直接用下面的明细格式；问题多时可增加简短索引表，但不能只交一张“建议完善字段、权限、异常”的泛化表。

```markdown
### R-01｜S2｜问题标题说明具体缺口

- 位置：文件＋章节/条款/表格行，或页码与短引文定位。
- 证据：必要原文；矛盾问题列出双方位置及各自规则。
- 问题与影响：哪项判断不明确；给出具体前提下可能出现的不同结果。
- 修改建议：需要补齐哪些决定或应统一到哪项已确认规则；有充分依据时给替换稿。
- 修复验收：修改后用什么场景确认歧义或矛盾已消除。
```

没有行号时不要人为发明行号；引用用户原文只取说明问题所需片段。范围遗漏的证据包含要求该能力的来源及已核对的章节范围，不用“搜索不到关键词”证明全文不存在。

严重性相同的问题按业务顺序或依赖关系排列。同一根因归并多个受影响位置；不同根因独立编号。不要设“最多十个问题”等任意上限截断实际发现；报告长时用文件承载完整明细并在回复给重点，不遗漏已发现项。

### 待确认与受限内容

待确认表：`编号｜需要决定的问题｜已知依据/建议｜影响条款及实施范围`。建议与已确认规则明确区分。

受限表：`资料或范围｜未取得/未读取原因｜因此无法验证什么`。没有受限或待确认内容时不生成空表。缺一张图不自动阻塞其他可审内容。

### 修订后的复核

复核表：`原问题编号｜已解决/部分解决/未解决/无法验证｜本次证据｜残留影响`。同时核对关联位置和验收条件，不以改动字数或关键词消失作为关闭依据。

## 3. 什么是足够具体的修改建议

- 差：“补充回款计划展示规则。”
- 好：“在详情3.2节补齐计划的数据范围、卡片字段、状态标签映射、排序及点击行为；目前只有新增入口，开发无法确定已有计划如何展示。”
- 差：“增加异常处理，保证系统健壮。”
- 好：“对批量移交中3条成功、1条权限校验失败的情况，确定是否保留成功项、失败记录在哪里展示、再次点击处理哪些记录；这三项决定当前文档均未定义。”

建议中的业务数字、角色、期限必须有来源或清楚标为待定方案。仅凭审查者经验不能决定全局唯一、自动删除历史、审批通过后自动发通知等产品政策。

## 4. 无明确缺陷时

可以直接报告“在已审范围内未发现影响开发和测试的明确缺陷”，说明实际检查范围及关键核对点。无需凑问题、写虚构风险或附大量可选建议。已确认的公共引用足够明确时不要求各页重复抄写。
